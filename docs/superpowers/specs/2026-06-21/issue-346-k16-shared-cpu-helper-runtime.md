# K16 Shared CPU Helper Runtime

> Issue: [#346](https://github.com/CertifiedBadIdeas/Compukter-Kraft/issues/346)

## Context

The K16 userland size report introduced in #345 measured the current production
userland duplication. The largest project-owned stable duplicate is
`k16-cpu-helpers.o .text.k16`: 16,632 retained bytes across 12 bundled
production userland programs.

This is the right first shared-runtime proof because the helper object is
already a distinct project runtime object. It is not Rust `core`, `alloc`,
`kraft-std`, libc, or libc++. Sharing it does not require solving a general
dynamic-linking ABI.

The current object ABI intentionally says that `k16-cpu-helpers` is an explicit
link input. Missing helper symbols are link-time errors. The linker and VM do
not synthesize helper bodies. The shared-runtime design must preserve that
strictness: a program either targets the shared helper runtime contract or it
embeds the helper object in the current static way. It must not silently fall
back at runtime.

## Decision

K16 should add a narrow shared CPU helper runtime before general shared
libraries.

The shared CPU helper runtime is a fixed runtime artifact installed by the
system image and mapped by the kernel into translated user address spaces. User
programs built for this runtime contain calls to stable helper entrypoints, but
they do not carry the helper text in their own payload. The kernel validates
the installed runtime artifact before launching such a program.

This is not a dynamic linker. There are no user-defined imports, no arbitrary
shared objects, no global symbol lookup, no per-process shared-library loader,
and no shared writable data. The first shared object is a versioned,
kernel-known runtime component with executable text and read-only metadata.

## Goals

- Remove duplicated `k16-cpu-helpers.o` text from normal production userland
  programs.
- Keep the first shared-runtime ABI small enough to implement and test before
  full shared libraries.
- Preserve deterministic failure behavior: missing or mismatched shared helper
  runtime artifacts fail launch explicitly.
- Keep current static helper linking available for BIOS, bootloader, kernel,
  tests, and standalone programs.
- Keep K16E dynamic user programs as the executable format for ordinary
  userland.

## Non-Goals

- Full shared libraries.
- ELF `ET_DYN`, dynamic symbols, PLT/GOT, or lazy binding.
- Sharing Rust `core`, `alloc`, `kraft-std`, libc, libc++, or user utility
  code.
- Shared writable data, TLS, constructors, destructors, or per-process runtime
  data sections.
- Demand paging, copy-on-write, or page-cache backed executable mappings.
- Silent fallback to embedded helpers when the shared runtime is missing.

## Runtime Artifact

The first implementation should introduce a dedicated K16 runtime artifact for
CPU helpers. The artifact should be generated by host tooling from the same
source as the current `k16 runtime k16-cpu-helpers` object, but packaged as a
kernel-loadable runtime image rather than linked into every user program.

The artifact must carry:

- a magic value identifying it as the K16 CPU helper runtime;
- an ABI version;
- a helper table version;
- executable payload bytes;
- one fixed entry offset for each exported helper;
- optional checksum or size metadata for validation.

The first storage location can be fixed OS policy, for example
`/lib/k16/cpu-helpers.krx`. The exact filename is less important than the rule:
the kernel loads one system-provided CPU helper runtime artifact and validates
it before launching shared-helper programs.

## Helper Table

The helper table is not a general symbol table. It is a fixed ABI table whose
entries are named by the current helper contract:

```text
__k16_halt_once
__k16_wait_once
__k16_yield_once
__k16_iret_once
__k16_save_trap_frame
__k16_restore_trap_frame
__k16_write_trap_vector
__k16_read_trap_cause
__k16_read_trap_pc
__k16_read_trap_value
__k16_read_trap_arg0
__k16_read_trap_arg1
__k16_read_trap_arg2
__k16_syscall_once
__k16_syscall0
__k16_syscall1
__k16_syscall3
__k16_iret_with_r0
__k16_write_interrupt_enable
__k16_write_interrupt_mask
__k16_read_interrupt_pending
```

Adding, removing, or changing an entry is an ABI-versioned change. The first
shared-helper program format must state the helper table version it expects.
The kernel rejects programs whose expected helper table version does not match
the installed runtime.

## User Program Contract

The next implementation slice should add a new build target or explicit linker
mode for shared-helper user programs, such as:

```text
k16 link --target program-dynamic --shared-cpu-helpers ...
```

The exact flag can change during implementation, but the behavior must be
explicit. A program linked in this mode:

- does not include `k16-cpu-helpers.o` in its retained sections;
- carries metadata saying it requires the K16 CPU helper runtime ABI version;
- carries relocation records that let the kernel patch helper call sites or
  call-table references at launch;
- still links all non-helper symbols normally;
- still fails at link time for unresolved non-helper symbols.

This keeps the no-fallback rule intact. A shared-helper program cannot run on a
system without the required runtime artifact, and a static-helper program does
not depend on the shared runtime.

## Loader And MMU Mapping

The kernel owns the shared runtime mapping policy.

For each translated user process that launches a shared-helper program, the
kernel should:

1. validate the shared CPU helper runtime artifact if it has not already done
   so for this boot;
2. allocate or reuse physical backing for the runtime text;
3. map that backing into the process address space at a kernel-selected
   read-only executable virtual range;
4. patch program helper relocations or helper-table references to point at the
   mapped runtime entrypoints;
5. enter user-translated mode normally.

The shared runtime mapping must be user-readable and executable, but not
user-writable. The first implementation may map one physical runtime copy into
multiple process address spaces. That is acceptable because the runtime has no
writable data.

The mapping address should be kernel-selected, not hard-coded into user
programs. A future implementation can reserve a high user-range band for shared
runtime mappings, but the shared-helper program format should not require a
fixed virtual address.

## K16E Metadata

The current K16E v2 dynamic user program format supports payload bytes and
relocation records. Shared CPU helper programs need one additional way to say
"this program requires helper runtime ABI N" and to distinguish helper
relocations from ordinary intra-image relocations.

There are two acceptable implementation paths:

1. add a small K16E v3 extension section for runtime requirements and helper
   relocations;
2. keep K16E v2 for static-helper programs and introduce a new `program`
   sub-kind only for shared-helper dynamic programs.

The preferred path is a K16E v3 extension because it keeps K16E as the single
guest-loadable executable container. The v3 design should remain specific to
the CPU helper runtime and must not become a general import/export ABI.

## Failure Behavior

Failures must be explicit:

- missing runtime artifact: launch fails with a kernel-visible executable or
  runtime-missing status;
- invalid runtime artifact: launch fails before user entry;
- helper ABI mismatch: launch fails before user entry;
- unsupported helper relocation: launch fails before user entry;
- helper mapping failure: launch fails with no-memory or mapping-failed status;
- attempt to write helper text: translated user fault.

The kernel must not fall back to static helper code when launching a
shared-helper program. The build mode chooses the contract.

## Compatibility

Static-helper user programs remain valid. BIOS, bootloader, kernel, standalone
programs, and low-level fixtures should continue linking `k16-cpu-helpers.o`
directly until there is a concrete reason to move them.

The shared-helper contract is production userland focused. Development test
programs may adopt it after the production path works, but they should not
drive the first ABI.

## Implementation Slices

1. **Format proof:** add a K16E metadata extension or explicit shared-helper
   target that can represent required CPU helper ABI version and helper
   relocation records. Verify with host-tool tests only.
2. **Runtime artifact proof:** generate and inspect a CPU helper runtime
   artifact with a fixed helper table. Verify table offsets and metadata.
3. **Kernel loader proof:** load the runtime artifact from storage, map it
   read-only executable into translated user processes, and patch helper
   references for one trivial user program.
4. **Production adoption:** build bundled production userland utilities in
   shared-helper mode and compare `reportK16UserlandSize` before/after.

Each slice should be separately reversible and should avoid full shared-library
semantics.

## Verification

The first implementation should prove:

- shared-helper linked programs no longer retain `k16-cpu-helpers.o` sections;
- static-helper linked programs still retain helpers and still run;
- missing or mismatched helper runtime artifacts fail launch explicitly;
- helper text is mapped read-only executable in translated user processes;
- `./gradlew-sandbox-dev :v1_21_1-neoforge:reportK16UserlandSize` shows the
  duplicated `k16-cpu-helpers.o` row disappear or materially shrink after
  production adoption.

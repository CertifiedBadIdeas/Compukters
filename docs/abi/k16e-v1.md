# K16E v1 K16 Executable

## Status

Status: experimental.

`K16E` is the guest-loadable executable container for K16 bootloader,
kernel, and user-space program images. It is the format firmware, boot loaders,
and future OS exec services should read from storage before copying image bytes
into guest RAM and jumping to an entry address.

The original fixed-image version intentionally supports one load section. It is
enough to separate "executable image file" from "raw instruction bytes" for the
bootloader, kernel, and standalone tool paths.

Dynamic user programs use the K16E v2 extension described below. K16E v3 adds
runtime requirement metadata for the kernel-known CPU helper runtime without
turning K16E into a general shared-library format. K16E v4 shared objects are
the first shared-library ABI container: they describe shareable code/read-only
payload bytes and a fixed export table, while leaving imports and kernel loader
mapping for later slices. These extensions keep boot/kernel fixed images intact
while giving the guest kernel enough metadata to load user programs at
kernel-selected addresses.

## Relationship To LLVM Objects

The first LLVM-facing toolchain must not make LLVM emit `K16E` directly.
`K16E` remains the final guest-loadable executable container produced by K16
tooling after LLVM has emitted a normal relocatable object.

This boundary keeps the VM independent from LLVM. LLVM-aware parsing,
relocations, symbols, sections, and target backend details belong to external
tooling. A VM or loader consumes validated `K16E` bytes and guest memory
ranges; it must not consume LLVM IR, LLVM object files, or LLVM-specific
metadata directly.

The intended static pipeline is:

```text
clang / llc
  -> K16 relocatable object
  -> k16 link
  -> K16E program/kernel/bootloader executable
  -> KFS or boot media installation
  -> VM loader or OS exec service
```

The relocatable object format, section names, relocation records, symbol
resolution rules, and unsupported relocation diagnostics are defined in
`k16-object-v1.md`. The conversion step selects the final `K16E` ABI kind
(`bootloader`, `kernel`, or `program`) and must reject unsupported object
features explicitly. Loaders must not reinterpret relocatable objects as
`K16E`, and LLVM-generated code must not bypass the normal `K16E` validation
rules.

## Relationship To Existing Targets

K16 artifact target meanings:

```text
boot     K16E v1 fixed image, ABI kind bootloader, linked at 0x00000800
kernel   K16E v1 fixed image, ABI kind kernel, linked at 0x00004000
program  K16E v1 user-space executable, ABI kind program, linked at 0x00015000
program-dynamic  K16E v2/v3/v6 user-space executable, ABI kind program, linked as base-relative offsets
program-dynamic imported  K16E v5 user-space executable, ABI kind program, with shared-library imports
program-dynamic imported+writable  K16E v6 user-space executable, ABI kind program, with shared-library imports and split writable data
shared-object    K16E v4 shared object, ABI kind shared-object, linked as base-relative offsets
bios     raw K16 bytes mapped as BIOS flash
```

Loaders and volume tools must not treat raw K16 bytes as a valid `K16E`
executable. Invalid magic is a hard decode error.

The current linker policy uses fixed load bases for fixed-image targets in the
512 KiB standalone guest RAM profile:

```text
0x00000800  bootloader payload load base
0x00004000  kernel payload load base
0x00015000  first user-space program payload load base
0x00080000  fixed-image standalone program stack top and payload end limit
```

Bootloader and kernel payloads are not capped by neighboring target load bases.
The fixed-image `program` target is still capped by the standalone program
stack top so linked user-space payloads cannot overlap that stack.
The `program-dynamic` target stores base-relative offsets and is not capped by
this fixed-image linker policy.
The loader still validates the address range encoded in each `K16E` image; it
does not silently relocate an oversized image.

These fixed bases and program bounds are linker/load-image policy, not the
complete runtime process memory model. In the current Rust kernel path, init's
process
`memory_end` is taken from profile v2 `BootInfo.ram_size`, and dynamic child
programs receive kernel-selected physical ranges inside the current foreground
process arena.

## Endianness

All multi-byte fields are little-endian.

## Header

The fixed header is 32 bytes.

```text
offset  size  name
0x00    4     magic
0x04    2     version
0x06    2     header_size
0x08    2     isa
0x0A    2     flags
0x0C    4     entry_pc
0x10    4     section_table_offset
0x14    4     section_count
0x18    4     abi_kind
0x1C    4     reserved1
```

Field values for v1:

```text
magic                 "K16E"
version               1
header_size           32
isa                   1  (K16)
flags                 0
section_table_offset  32
section_count         1
abi_kind              1  (bootloader), 2  (kernel), or 3  (program)
reserved1             0
```

`entry_pc` is the guest physical address where execution starts after all load
sections have been copied. In v1 this is part of a trusted fixed-image ABI:
the image describes where it was linked to run, and the loader must reject it
if that range is not allowed by the current boot or exec policy.

ABI kind values:

```text
1  bootloader
2  kernel
3  program
4  shared-object
```

The `program` kind is the first filesystem-backed user-space executable
profile. It is intended for OS-level `spawn(path, argv)` style services: the OS
resolves paths and reads file bytes from storage, then validates and loads a
`K16E` program image. Host APIs must not accept guest filesystem paths.

The first `program` compiler profile links code at `0x00015000`. This address
is part of the program target profile; guest source code does not choose an
arbitrary load address. A kernel or exec service must still validate that a
program image fits the process memory range selected for execution.

## Section Record

The v1 section table contains exactly one 20-byte load-section record.

```text
offset  size  name
0x00    4     kind
0x04    4     load_addr
0x08    4     file_offset
0x0C    4     file_size
0x10    4     memory_size
```

Field values and rules:

```text
kind         1  (load)
file_offset 52
file_size   non-zero K16 byte length
memory_size greater than or equal to file_size
```

`load_addr` is the guest physical address where the payload bytes are copied.
`entry_pc` must point inside the loaded memory range and must be 2-byte
aligned.

If `memory_size` is larger than `file_size`, the loader must zero-fill the tail
from `load_addr + file_size` up to `load_addr + memory_size`. This is the v1
representation for trailing `.bss`-style program memory.

## Loader Algorithm

A loader should:

1. Read and validate the fixed header.
2. Validate the single section record.
3. Check that the payload byte range is present in the file.
4. Check that `load_addr + memory_size` does not overflow and fits in the
   target guest RAM range.
5. Copy `file_size` bytes from `file_offset` to guest RAM at `load_addr`.
6. Zero-fill `memory_size - file_size` bytes after the copied payload.
7. Start or jump to `entry_pc`.

No loader should guess an entry address from file position, reinterpret a
different ABI kind, or fall back to raw instruction bytes.

For `program` images, the normal path is:

```text
OS filesystem -> read K16E file bytes into RAM -> exec service validates ABI kind program -> load payload -> enter entry_pc
```

The exec service receives bytes or guest RAM ranges, never a host-side path.
The VM runtime provides the filesystem read and `program` ABI kind validation
boundary for already-read bytes. The first guest-side kernel loader now
exercises the same policy directly from storage: it reads `/bin/init.kx` from
the `ROOT` KFS partition, validates ABI kind `program`, copies the payload to
`load_addr`, and jumps to `entry_pc`.

## Dynamic User Program Extension

K16E v2 dynamic user programs are `program` ABI artifacts that do not carry a
fixed physical load address. The kernel loader chooses the load base, copies the
payload, zero-fills the dynamic memory tail, and applies the relocation table
with the selected base.

Host tooling emits this format with `k16 link --target program-dynamic`. This
target is a single dynamic user-program target, not a per-process address-window
scheme.

The current Rust kernel records a guest-physical memory range for each
foreground process and validates syscall buffers against the current process
range. Dynamic user-program images participate in that physical layout, but the
extension does not imply virtual memory, page tables, or address translation.

The fixed header fields keep the same offsets with these v2 meanings:

```text
version        2
entry_pc       entry_offset relative to the selected load base
section_count  2
abi_kind       3  (program)
```

The section table contains a load section followed by a relocation section:

```text
section 0 kind         1  (load)
section 0 load_addr    0
section 0 file_offset  72
section 0 file_size    payload byte length
section 0 memory_size  dynamic memory size

section 1 kind         2  (relocations)
section 1 load_addr    0
section 1 file_offset  72 + payload byte length
section 1 file_size    relocation_count * 8
section 1 memory_size  relocation_count
```

Each relocation record is 8 bytes:

```text
offset  size  name
0x00    4     offset
0x04    4     kind
```

Relocation kinds:

```text
1  abs32
2  call32
```

`offset` is relative to the start of the dynamic payload. The first supported
relocations patch 32-bit fields that represent guest addresses. A dynamic
loader must reject relocation ranges outside the dynamic memory size, odd
relocation offsets, unsupported relocation kinds, non-zero load addresses, and
non-`program` ABI kinds. It must not silently reinterpret a fixed-image K16E v1
artifact as dynamically relocatable.

## CPU Helper Runtime Requirement Extension

K16E v3 dynamic user programs extend K16E v2 with runtime requirement metadata
for the kernel-known CPU helper runtime. Host tooling emits this format only
when `k16 link --target program-dynamic --shared-cpu-helpers` is used.

This extension is not a dynamic linker and not a shared-library ABI. It does
not define arbitrary imports or exports, dynamic symbol lookup, GOT/PLT, TLS,
shared writable data, constructors, destructors, or user-provided shared
objects. It only says that the executable requires a CPU helper runtime ABI and
contains call sites or address fields that the kernel loader must patch to
fixed helper table entries after it has selected and mapped that runtime.

The fixed header fields keep the same offsets with these v3 meanings:

```text
version        3
entry_pc       entry_offset relative to the selected load base
section_count  4
abi_kind       3  (program)
```

The section table contains the v2 load and relocation sections, followed by a
CPU helper requirement section and a CPU helper relocation section:

```text
section 0 kind         1  (load)
section 0 load_addr    0
section 0 file_offset  112
section 0 file_size    payload byte length
section 0 memory_size  dynamic memory size

section 1 kind         2  (relocations)
section 1 load_addr    0
section 1 file_offset  112 + payload byte length
section 1 file_size    relocation_count * 8
section 1 memory_size  relocation_count

section 2 kind         3  (CPU helper requirement)
section 2 load_addr    0
section 2 file_offset  section 1 file_offset + section 1 file_size
section 2 file_size    8
section 2 memory_size  1

section 3 kind         4  (CPU helper relocations)
section 3 load_addr    0
section 3 file_offset  section 2 file_offset + 8
section 3 file_size    cpu_helper_relocation_count * 12
section 3 memory_size  cpu_helper_relocation_count
```

The CPU helper requirement record is 8 bytes:

```text
offset  size  name
0x00    4     CPU helper runtime ABI version
0x04    4     helper table version
```

Each CPU helper relocation record is 12 bytes:

```text
offset  size  name
0x00    4     offset
0x04    4     kind
0x08    4     helper id
```

CPU helper relocation kinds match the current dynamic relocation width:

```text
1  abs32
2  call32
```

CPU helper ids are fixed ABI table indexes, not symbol-table entries. A loader
must reject unsupported helper ids, unsupported CPU helper relocation kinds,
odd relocation offsets, ranges outside dynamic memory, missing runtime
artifacts, invalid runtime artifacts, and CPU helper ABI or helper table
mismatches. It must not fall back to embedded `k16-cpu-helpers.o` text for a
K16E v3 shared-helper program.

The old K16E v3 CPU helper runtime requirement remains a narrow experiment and
is superseded as the main implementation path by this shared object ABI. New
shared-runtime work should target K16E v4 shared objects instead of adding more
kernel-known special runtime artifacts.

## Shared Object Extension

K16E v4 shared objects are the first shared-library ABI container. They are not
directly executable user programs and do not carry an entrypoint. They contain
base-relative payload bytes, base-relative relocation records, and a fixed
export table that later executable imports can bind to. The K16 kernel loader
maps a needed shared object after the importing program image and applies the
shared object's own relocation records with that library load base.

This first v0 container does not define writable per-process library data, TLS,
constructors, destructors, lazy binding, symbol hashing, library version
matching, or a multi-directory search path. Those are follow-up ABI slices.

The fixed header fields keep the same offsets with these v4 meanings:

```text
version        4
entry_pc       0
section_count  3
abi_kind       4  (shared-object)
```

The section table contains a load section, a relocation section, and an export
section:

```text
section 0 kind         1  (load)
section 0 load_addr    0
section 0 file_offset  92
section 0 file_size    payload byte length
section 0 memory_size  shared object memory size

section 1 kind         2  (relocations)
section 1 load_addr    0
section 1 file_offset  92 + payload byte length
section 1 file_size    relocation_count * 8
section 1 memory_size  relocation_count

section 2 kind         5  (exports)
section 2 load_addr    0
section 2 file_offset  section 1 file_offset + section 1 file_size
section 2 file_size    export section byte length
section 2 memory_size  export count
```

Shared-object relocation records use the same 8-byte record shape and relocation
kind values as dynamic user program relocations. `offset` is relative to the
start of the shared object payload, and the loader adds the shared object's
process-local load base to the referenced field.

Each export record is 8 bytes:

```text
offset  size  name
0x00    4     name_offset
0x04    4     exported payload offset
```

`name_offset` is relative to the export section string table, which starts
immediately after the fixed export records. Export names are UTF-8 and
NUL-terminated. The export section is padded to an even byte length. Exported
payload offsets are base-relative and must be 2-byte aligned inside the shared
object memory size.

K16E shared object v0 does not define imports. The kernel loader must map
executable/read-only shared pages separately from per-process writable data
when later slices add data sections. A loader must reject shared objects with
non-zero entry offsets, non-zero load addresses, malformed export string
tables, unsupported relocation records, unsupported ABI kinds, or export
offsets outside the shared object memory size. It must not silently fall back
to statically linked copies when a program declares a shared dependency.

## Imported Dynamic Program Extension

K16E v5 imported dynamic programs extend v2 with shared-library dependency
metadata. They are still `program` ABI artifacts and still use base-relative
payload bytes. The extra metadata declares which shared libraries the program
needs and which payload fields must be patched to exports from those libraries.

This v0 import container defines the initial kernel loading path for libraries
under KFS `/lib`. It does not define library version matching, symbol hashing,
lazy binding, GOT/PLT layout, writable library data, TLS, constructors, or
destructors.

The fixed header fields keep the same offsets with these v5 meanings:

```text
version        5
entry_pc       entry_offset relative to the selected load base
section_count  4
abi_kind       3  (program)
```

The section table contains a load section, the normal dynamic relocation
section, a needed-library string table, and an import relocation section:

```text
section 0 kind         1  (load)
section 0 load_addr    0
section 0 file_offset  112
section 0 file_size    payload byte length
section 0 memory_size  dynamic memory size

section 1 kind         2  (relocations)
section 1 load_addr    0
section 1 file_offset  112 + payload byte length
section 1 file_size    relocation_count * 8
section 1 memory_size  relocation_count

section 2 kind         6  (needed libraries)
section 2 load_addr    0
section 2 file_offset  section 1 file_offset + section 1 file_size
section 2 file_size    needed library string table byte length
section 2 memory_size  needed library count

section 3 kind         7  (import relocations)
section 3 load_addr    0
section 3 file_offset  section 2 file_offset + section 2 file_size
section 3 file_size    import relocation section byte length
section 3 memory_size  import relocation count
```

Needed library names are UTF-8 and NUL-terminated. The section is padded to an
even byte length.

Each import relocation record is 16 bytes:

```text
offset  size  name
0x00    4     offset
0x04    4     kind
0x08    4     library_index
0x0C    4     symbol_name_offset
```

`offset` is relative to the start of the dynamic payload. `kind` uses the same
values as the normal dynamic relocation section. `library_index` indexes the
needed-library list. `symbol_name_offset` is relative to the import relocation
section string table, which starts immediately after the fixed import
relocation records. Import symbol names are UTF-8 and NUL-terminated.

The K16 kernel loader resolves each needed library from the `ROOT` KFS
partition under `/lib/<needed-library>`. Needed-library names are single KFS
path components, not full paths. A loader must reject missing needed libraries,
missing exported symbols, unsupported import relocation kinds, out-of-range
library indexes, and malformed import string tables. It must not silently fall
back to statically linked copies when a program declares imports.

## Writable Dynamic Program Segment Extension

K16E v6 dynamic programs split writable program memory from executable/read-only
program memory. Host tooling emits this format when a `program-dynamic` image
retains `.data` or `.bss`. The split exists so MMU loaders can preserve user
W^X: code and readonly data are mapped executable/read-only, while writable C
globals are mapped writable/non-executable.

The fixed header fields keep the same offsets with these v6 meanings:

```text
version        6
entry_pc       entry_offset relative to the selected load base
section_count  3 for no imports, 5 with imports
abi_kind       3  (program)
```

The first three section records are:

```text
section 0 kind         1  (load)
section 0 load_addr    0
section 0 file_offset  92 or 132 depending on section_count
section 0 file_size    executable/read-only payload byte length
section 0 memory_size  executable/read-only memory size; also writable offset

section 1 kind         8  (writable load)
section 1 load_addr    writable offset
section 1 file_offset  section 0 file_offset + section 0 file_size
section 1 file_size    initialized writable byte length
section 1 memory_size  page-rounded writable memory size

section 2 kind         2  (relocations)
section 2 load_addr    0
section 2 file_offset  section 1 file_offset + section 1 file_size
section 2 file_size    relocation_count * 8
section 2 memory_size  relocation_count
```

For imported v6 programs, section 3 is the v5 needed-library section and
section 4 is the v5 import-relocation section. The writable offset must be
non-zero and 4 KiB page-aligned. The writable memory size must be a non-zero
multiple of 4 KiB and includes any `.bss` zero-fill plus page padding. Loaders
must zero-fill the writable memory tail and any omitted gap bytes before
entering the program. A loader must not map any user page as both writable and
executable.

## Storage Volume Tooling

`K16E` is the artifact format produced by the compiler. The current `K16VOL`
storage tooling installs fixed-image `K16E` artifacts into the partitioned
system volume:

- `put-boot` accepts ABI kind `bootloader` and writes
  `BOOT`/KFS `/boot/loader.kb`.
- `put-kernel` accepts ABI kind `kernel` and writes
  `ROOT`/KFS `/boot/kernel.kx`.
- `program` artifacts are not installed by `k16 volume put-boot` or
  `put-kernel`; they belong in a filesystem such as `KFS` and are selected by
  OS policy.

The storage layout is defined in `k16-storage-volume-v1.md`.

## Validation Errors

A decoder must reject:

- invalid magic;
- unsupported version;
- unsupported header size;
- unsupported ISA;
- non-zero flags;
- unsupported section table offset;
- section count other than `1`;
- unsupported ABI kind;
- non-zero reserved header fields;
- unsupported section kind;
- payload offset other than `52`;
- empty payload;
- odd K16 payload length;
- `memory_size < file_size`;
- odd K16 memory length;
- payload range outside the file;
- load range overflow;
- `entry_pc` outside the loaded memory range;
- unaligned `entry_pc`.
